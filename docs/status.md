## The one thing to know

Everything below is headless-, software-render- and (where stated) real-backend-verified. **Headset testing is ongoing and informal, and this repo does not record which features have been checked by hand**; nothing has been measured on Quest hardware (PCVR via Virtual Desktop is the main route so far). "Built" does not mean "good in the hand". When the owner reports a feature checked or a bug found, record it here and in the [status log](status-history/status-log.md) (its "Untested paths" section is the older open-verification list).

## Open items that matter most

0. **First native Quest 3 run (21 Oct 2026, owner's report):** the APK starts on the landing and demo models feel smooth; five bugs found (monolith laser too short, colour flicker looking up on the landing, Open leaves the monolith for the tablet, an unsaved-changes prompt on a handled demo offered only on the tablet, passthrough black, so no QR scan yet). Causes and plan: [`quest-first-run-fixes.md`](quest-first-run-fixes.md). **Passthrough (B5) fixed in the project, not yet rebuilt or tried on the headset:** the headset said "blend modes: opaque, the passthrough layer failed to start", because the Vendors plugin reads the passthrough / scene settings in the editor at export and they were Android-only, so the manifest lacked them. They now also carry `.editor_hint` (`android-build.md`, the Android-only setting trap). A second cause, confirmed: the owner's export preset had **Enable Meta Plugin** off (`xr_features/enable_meta_plugin=false`, the plugin's default), which leaves every Meta entry out of the APK; with it on (third APK) the spatial-data permission is asked for, but Passthrough shows the B2 flicker (black / orange / light in each eye) instead of the room; Settings > Graphics check on the monolith (live switches for each suspect) is built to find which part causes it. The app no longer starts in Passthrough (it did, because the last scene is remembered, and that run was blind from the start). Each eye showed one flat colour; the Vendors plugin's Meta dynamic resolution (on by default, sets a render region every frame) is the suspect and is now off in `project.godot`, not yet tried on the headset. The startup log then showed foveated rendering through Vulkan's fragment density map (the new top suspect); `user://graphics.cfg`, pushed with adb, sets foveation, VRS, MSAA and the landing's sky / fog / glow / rockets at startup so they can be tried without seeing a menu or rebuilding. **Confirmed by the owner: foveated rendering causes it** (toggling it cures and returns it); `openxr/foveation_level` is now 0. Still to try: foveation 2 with the viewport's VRS set to XR. **Passthrough works on the headset**, and a QR code was read; connecting failed (B6: most likely no Internet permission in the export preset). **B1, B3, B4 fixed** (monolith reach 5 m, an Open a file page on the monolith, demos never ask and the Discard / Cancel choice on the monolith), headless-tested, not yet on the headset; pairing feedback reworked (B6). The other four are not fixed yet.
1. **Quest-native numbers.** Load time and frame rate on Quest hardware; informal headset testing continues on everything else.
2. **Plain HTTP on the Quest: untested.** Long assumed blocked by Android, but its cleartext rule applies to Java networking and Godot's `HTTPRequest` uses its own sockets, so a LAN `http://` server probably works. Try it on the headset first ([`landing-scope.md`](landing-scope.md#plain-http-on-the-quest)); HTTPS (e.g. a Cloudflare Tunnel) remains the safe choice.
3. **Server does not guard cycles or unknown Part ids** on `POST /parts/{id}/occurrences`; the client refuses them (see [`backend-api-notes.md`](backend-api-notes.md)).
4. **Design table not built:** surfacing family, curves, gear chain / planetary / bevel pair (single gears, racks and bevel gears are on the table since gears-and-motion M2), constrained sketch drag, sketch pattern/mirror, loft guide curves, feature mirror/pattern, extrude profile selection, dragging tree rows out, sub-assemblies on the table. Authoritative list: [`design-table.md`](design-table.md) and [`design-table-gaps.md`](design-table-gaps.md). Check them before relying on this summary; Phase 7 closed some.
5. **Multi-file assemblies** now resolve client-side on Open / Add (`scripts/native_compose.gd`, a port of the flat app's composer with the `.DIDSAprt` / `.didsa` fallback, numbers kept exactly as written). Verified against a live backend (`tests/e2e_bug_report.gd`), not on the headset. A clashing Part id between two files is reported, not re-minted. **Moved files** (20 Oct, DIDSA-CAD `docs/moved-files-scope.md` F2): a part file that moved or was renamed is found by its part id in the opened file's folder, the project folder and the models folders (every subfolder); several matches, a different file at the path or a name-only match are listed on **Files > References** to pick from (Locate... lists every model file), never loaded silently. Headless (`tests/moved_files.gd`, `tests/file_lookup_vectors.gd`) and live backend (`tests/e2e_moved_files.gd`); not on the headset. Picks only for the opened file, not for Add or a room.
